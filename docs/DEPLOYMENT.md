# Production deployment

## Render (database already provisioned)

The repository contains a [`render.yaml`](../render.yaml) Blueprint: one **web service** (builds the SPA and the API;
the API serves the SPA and runs the scheduler workers in-process) plus a **Key Value** (Redis) instance.

1. Render dashboard → **New → Blueprint** → select this GitHub repository → apply.
2. Fill the `sync: false` variables when prompted:
   * `DATABASE_URL` = the Postgres instance's **Internal Database URL** (the service and database must be in the same region).
   * `APP_URL` and `CORS_ORIGINS` = the service URL, e.g. `https://orgpm.onrender.com`.
   * `ADMIN_EMAIL` / `ADMIN_PASSWORD` = the first Super Admin. On startup the API applies migrations and base data
     (roles, permissions, default rules) and creates this admin **only if the users table is empty**.
3. Deploy and open the URL. Each organization registers itself from the sign-in page (**Register organization**) and gets
   an isolated tenant; set `ALLOW_REGISTRATION=false` to disable self-service sign-up. `ADMIN_EMAIL`/`ADMIN_PASSWORD` is
   optional: it creates a Super Admin in the default organization when the database has no users.

Render's database user is not a superuser, so PostgreSQL row-level security (tenant isolation) is enforced — the API logs a
warning at startup if it ever connects as a superuser.

JWT secrets are generated by Render. Optional channel credentials (SMTP, VAPID, FCM, WhatsApp) are added as extra
environment variables. Notes for the free plans: the service sleeps when idle (reminders fire when it wakes — the
sweeper catches up on anything missed), Key Value data is not persisted (PostgreSQL remains the source of truth and
jobs are re-armed automatically), and the local disk is ephemeral (attach a Render Disk for durable uploads).
For always-on scheduling use a paid web service, or run `node dist/worker.js` as a Background Worker with
`RUN_WORKERS_IN_API=false` on the web service.

Connecting from outside Render (e.g. running migrations locally) uses the **External Database URL** with TLS:
put it in a git-ignored `server/.env.render` (`DATABASE_URL=…` and `DATABASE_SSL=true`) and run
`set -a && . ./.env.render && set +a && npm run seed` in `server/`. TLS is enabled automatically for `*.render.com` hosts
(`DATABASE_SSL=auto`).

## Linux server with Docker

### 1. Server prerequisites
Ubuntu 22.04/24.04 (or any Linux with Docker Engine 24+ and the compose plugin), 2 vCPU / 4 GB RAM minimum,
a DNS name, and ports 80/443 open.

```bash
curl -fsSL https://get.docker.com | sh
sudo usermod -aG docker $USER   # re-login
git clone <your-repo> orgpm && cd orgpm
cp .env.example .env
```

Edit `.env`: strong `POSTGRES_PASSWORD` (application role) and `POSTGRES_ADMIN_PASSWORD` (superuser, administration only), 64-char random `JWT_ACCESS_SECRET`/`JWT_REFRESH_SECRET`
(`openssl rand -hex 32`), `APP_URL`/`CORS_ORIGINS` = your https origin, `ADMIN_EMAIL`/`ADMIN_PASSWORD` for the first
Super Admin, and any notification channel credentials (see docs/NOTIFICATIONS.md). The API refuses to start in
production with default secrets.

### 2. Start
```bash
docker compose up -d --build
docker compose exec api node dist/db/seed.js        # roles, permissions, default rules, first Super Admin
docker compose ps && curl -s localhost:8080/api/health
```
Migrations run automatically at API/worker start (guarded by a PostgreSQL advisory lock). Sign in with ADMIN_EMAIL,
then create departments and employees (temporary passwords must be changed at first login).

### 3. TLS / reverse proxy
Put Caddy, Traefik or host nginx in front of `web:80` (published on `WEB_PORT`, default 8080). Example Caddyfile:
```
orgpm.example.com {
  reverse_proxy 127.0.0.1:8080
}
```
Cookies are `Secure` + `SameSite=Strict` in production, so the app must be served over HTTPS. Express trusts one proxy hop.

### 4. Scaling
* `docker compose up -d --scale worker=3` — BullMQ distributes jobs; row locks and dedupe keys prevent duplicates.
* API instances can be scaled behind a load balancer; Socket.IO events are relayed through Redis pub/sub
  (enable sticky sessions on the balancer for the Socket.IO long-polling fallback).
* Redis runs with AOF and `noeviction` — never use an eviction policy for BullMQ.

### 5. Backups & restore
PostgreSQL holds all business data (Redis is rebuildable: the sweeper re-arms jobs from `notification_schedules`).
```bash
# nightly backup (cron)
# run as the postgres superuser: forced row-level security blocks pg_dump for the app role
docker compose exec -T postgres pg_dump -U postgres -Fc orgpm > backups/orgpm-$(date +%F).dump
docker run --rm -v orgpm_uploads:/u -v $PWD/backups:/b alpine tar czf /b/uploads-$(date +%F).tgz -C /u .
find backups -mtime +30 -delete

# restore
docker compose stop api worker
docker compose exec -T postgres pg_restore -U postgres -d orgpm --clean --if-exists < backups/orgpm-2026-11-21.dump
docker run --rm -v orgpm_uploads:/u -v $PWD/backups:/b alpine sh -c "cd /u && tar xzf /b/uploads-2026-11-21.tgz"
docker compose start api worker
```
Test restores regularly on a staging host. Keep backups off-site (S3/Backblaze via rclone).

### 6. Monitoring & logs
* Health: `GET /api/health` (DB connectivity) — wire to Uptime Kuma / your monitor; containers have Docker healthchecks.
* Logs: structured JSON (pino) on stdout → `docker compose logs -f api worker`, or ship with Loki/Promtail, Vector or CloudWatch.
  Authorization headers and cookies are redacted.
* Notification health: **Reminders → Delivery log** shows sent/delivered/failed/retried/skipped counts; permanent
  failures create in-app alerts for Super Admins.
* Audit: **Administration → Audit log** (append-only).

### 7. Upgrades
```bash
git pull && docker compose up -d --build   # migrations apply on start
```
Migrations are forward-only SQL files in `server/migrations`; add a new numbered file for every schema change.

### 8. Without Docker (systemd)
Build: `cd server && npm ci && npm run build`, `cd web && npm ci && npm run build`. Run `node dist/index.js` (API) and
`node dist/worker.js` (worker) as two systemd services with the environment from `server/.env.example`; serve
`web/dist` with nginx using `web/nginx.conf` (change `proxy_pass` to `http://127.0.0.1:4000`). Alternatively set
`SERVE_WEB=true` to let the API serve the SPA from `web/dist` on the same origin.
